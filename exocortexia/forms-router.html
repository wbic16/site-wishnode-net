Forms Intake Router

Forms intake with an explicit state machine — and no personal information by design

What it does

Agencies receive forms — the demo is built for public-records request intake — and each submission must be classified, routed to the owning office, worked, and closed, with its progress visible to the requester. Forms Router makes that lifecycle explicit and auditable.

  • No PII by design. The form's fields are agency, subject, description, and date_range. There are no name, email, or contact fields: routing a request needs none of them, so the form never asks. The page carries a prominent banner: SYNTHETIC DATA ONLY — DO NOT ENTER PERSONAL INFORMATION.
  • Tracking without an account. Each submission gets a tracking code derived from the first 10 hex characters of sha256(form + sequence + values). The requester follows status with the code alone — no account, no email round-trip.
  • A strict, enumerated state machine. received → routed → in_review → closed are the only legal transitions — 3 of the 16 possible state pairs. The test suite enumerates all 16 pairs; an illegal transition (say, routed straight to closed) is rejected with HTTP 400 and writes nothing: no history line, no audit entry.
  • Spec-driven forms. The form is rendered from a data spec stored as a phext scroll, not hard-coded in the page — changing the form means changing the spec.
  • CSV export. All submissions export as RFC 4180 CSV (code, form, state, agency, subject).

Why the state machine matters

Most intake systems have an implicit state machine: statuses that drift, transitions nobody enumerated, and records that end up in combinations the process never intended. Naming the states and transitions — and testing the illegal combinations, not just the happy path — is what turns a status field into a guarantee. The full state-machine sheet is in the repository: docs/forms-router-statute.md.
